## 建模提示

评分看「可浏览、可检索、有店铺点位 + 数据驱动场景变化」，示意级别即可，不做 1:1 精模：

- 店铺：把导览牌店名/铺位号录成数组，循环生成方块，绑定状态（绿有位/黄排队/红满）；
- 扶梯：斜面 + 等距台阶 + 扶手（可做滚动动画）；
- 电梯：透明竖井 + 沿 Y 轴移动的轿厢；
- 中庭挑空：楼层平面中间开洞（几块盒子拼成环形）。

### 1. 格式：`izi/` 32 张后缀已改为 `.webp`（原为假 PNG，E-01 已处置）

| 目录 | 后缀 | 真实格式 | 结论 |
| --- | --- | --- | --- |
| `izi/` | **.webp ×32** | **WEBP ×32** | ✅ 已对齐（2026-11-26 E-01） |
| `netease/` | .jpg ×26 | JPEG ×26 | 一致 |
| `official/` | .jpg ×6 / .png ×1 | JPEG ×6 / PNG ×1 | 一致 |

**原问题**：这批图是 iziRetail 导出时被存成 WEBP 却沿用 `.png` 后缀的「假 PNG」。浏览器按魔数嗅探，`<img src="*.png">` 也能显示，所以演示不受影响；但 Blender 贴图、ImageMagick、部分构建工具会直接报 `not a PNG`，评委翻素材目录也会看出不符。

**处置结果（E-01，2.26 MB 全量转正）**：
- 32 个文件 `git mv` 为 `.webp`，**未重新编码**，像素与体积零变化（若转真 PNG，照片类内容体积会涨到 20–30 MB，得不偿失）。
- 全仓库无任何代码引用这批图（`grep -rn izi src/ index.html` 无命中），改后缀无运行时风险。
- `docs/` 内 16 处 `izi_XX.png` 引用同步改为 `.webp`。
- **防复发**：资产校验已统一为 `scripts/check-assets.mjs`（E-04 CI 的 `assets` job 直接调用）。它除「后缀与真实格式不符 / 空文件」外，还查单文件体积、总体积与文件名 ASCII，覆盖面比最初的 Python 版更全；原 `scripts/check_asset_formats.py` 已删除以免两套逻辑各改各的。本地跑 `node scripts/check-assets.mjs` 即可。

### 4. 6–8F 点位定位方法（导览牌已到，仍须校正）

1. **优先用 C 实拍导览牌** `floor-guide-6f/7f/8f.jpg` 读铺位号与店名（见下节）；
2. **主力店位置**用导览牌位置 + 门头照片交叉定位（腾讯新闻已给 7–8F 等位最密）；
3. 导览牌是**斜角翻拍**，有反光与透视变形：铺位号可读，但**坐标不能直接量取**，须按柱网、中庭、扶梯位置校正；
4. 每个点位在 JSON 里标 `verified: "observed"`（现场拍到门头并确认位置）或 `public` / `unverified`（见 `CONTRACTS.md` §二三级定义），UI 显示依据级别。注意：契约只有 `observed` / `public` / `unverified` 三级，旧稿里的 `field-photo` 不是合法值，`scripts/check-stores.mjs` 会判非法；
5. **不得**把校正后的估算坐标写成实采坐标——这是当前代码里已经犯过的错（太二写成 7F 实为 8F、喜茶写成 6F 实为 1F）。
