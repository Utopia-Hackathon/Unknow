## 一、痛点主体

| 角色 | 被卡住的是什么 |
| --- | --- |
| **门店迎宾 / 排号岗**（直接主体） | 每来一位顾客要重新判断一次：这张空桌给谁、下一位是谁、要不要跳过叫不到的那一位。判断依据在脑子与手上，不在系统里 |
| **等位顾客**（受影响方） | 不知道还要等多久、不知道自己为什么被后来的人超过，只能反复去问；问完一部分直接走了 |
| **门店经营**（最终承担方） | 空出来的桌没能立刻坐人，等位的客人没留住——翻台与客流两头损失，且这两笔损失都没有被记录 |

## 二、发生环节

等位流程四步，痛点集中在后两步：

```
到店 → 取号 ────────→ 等位 ──✕──→ 叫号 ──✕──→ 入座
       (有号)        (不知时长)   (桌型错配)   (人不在则空转)
```

- **断点一（叫号 · 桌型错配）**：空出的桌有桌型限制（几人桌），排最前的顾客不一定坐得下。为了让桌子不空着，店员会跳过他去叫后面桌型合适的人——**从队首顾客视角看就是「后来的人先进去了」**。
- **断点二（入座 · 过号空转）**：被叫到的顾客暂时不在场（去买东西、在别处等），店员无法判断该等多久，桌位在此期间空置；同时后面的人在等这张桌被释放。

**关键点：两个断点都不是「员工不负责」，而是「缺一个把桌型、排队、时长摊开的信息面」。** 规则本身是合理的（桌型匹配能提高翻台），问题在于规则不透明、损失不可见。

第 2 条是全单最关键的一条：它解释了「明明在排队，为什么规则不透明」。但它是**观察加推断**，本方案不把它当既定事实，而是作为需要被数据验证的假设——这正是赛道要求的「假设推演」的入口。

## 四、现有手段为什么解决不了

门店并非没有排号工具，但现场处置仍依赖人：

1. 跳号与过号都需要**实时掌握桌位状态**（哪张桌、坐几人、还需多久翻台），而这类状态在多数门店不是结构化数据；
2. 顾客侧的等待时长是**口头告知**，无依据，说服力弱；
3. 两个断点造成的损失（空置时长、流失人数）**没有被记录**——看不见的损失不会被优化。

## 五、本痛点对应的经营指标

**主指标：顾客流失率**（定义与口径见 `docs/METRICS_DEF.md`，裁决见 D010）。

选它的理由：它是 E17 唯一有现场观察支撑的指标，且正是「顾客问完等待时长后离开」这一行为的直接计量——痛点与指标同源，评委追问「这个指标为什么能说明价值」时有据可答。

方案要做的事：把三个决策点（叫谁 / 叫不到怎么办 / 还要等多久）摊在同一块屏上，用假设推演看不同规则下的流失率差异。

| 痛点环节 | 对应功能 | 对应验收 |
| --- | --- | --- |
| 断点一：桌型错配导致跳号 | F02-01 按桌型匹配叫号 + 解释跳号原因 | A04 |
| 断点二：叫号无人应答 | F02-02 过号回捞 | A05 |
| 后果：顾客流失 | F02-03 流失记录 + 指标计算 | A06 / A07 |

## 六、证据强度与口径声明

- 以上观察为 **2026-11-23、11-24 两天、单点商圈（正弘城）、无计数工具**的现场记录，**样本有限，不作为统计结论使用**。
- 期间**未取得商户访谈授权**（商户不欢迎以访谈/调查为目的的人群，E14），故不引用任何商户经营数据。
- 系统内运行与演示的全部数据为**模拟数据**，未接入任何真实商业系统，不做真实支付。
- E17 的「约一半」为**现场观察估计，非精确计数**，仅用于校验模拟基线的量级，不作为精确基线。
- 第 2 条依据的机制解释为**团队推断**，在方案中作为待验证假设，不写成事实。
